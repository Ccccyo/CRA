# 案件自动进入 RAG：实现与边界

## 业务判断

案件数据库是当前事实和流程状态的权威来源。RAG 中的 `case_evidence` 是它的**派生、可检索快照**，用于回答“本案当前材料、财务证据、人工处理和流程到哪一步”等问题；它不是正式授信政策、原始财报，也不能把历史决定自动变成本次审批结论。结构化额度、状态及确定性计算仍应直接查数据库/程序，不以文本检索结果替代。

“所有案件自动入库”指每个 `cra_case`/`cases` 行都有一个对应的 `case_evidence` 文档，不是把全部案件开放到公用知识目录。`case_evidence` 仅在明确 `case_id` 的案件上下文中检索；角色授权仍由可信服务执行。现有角色模型允许具备案件读取权限的分析人员查看工作台案件，**尚无逐案件 ACL**。若真实组织需要按客户、地区或所有人细分访问，必须先补授权模型再接真实敏感案件。

## 已实现的数据流

`案件写入（创建/更新标题/笔记/流程） → 同步当前 DB 状态 → 按标题切分 → 知识文档/片段表 → knowledge_revision 变化 → 下次检索重建进程索引 → 本案权限过滤 → 引用`

- 来源：案件基本信息、输入材料索引、流程状态、已确认主体、财务证据、风险意见、人工处理记录。仅存结构化状态和来源描述；不自动复制 Excel/PDF 原始字节，也不把未经复核的 OCR 当作已签署财务事实。
- 主键：`case-evidence-{sha256(case_id)[:24]}`；片段 ID 由文档 ID 与章节序号组成。`content_hash` 保证内容未变时不重复写入；改名、重新上传、财务签署和状态变化会替换旧片段，避免把旧值与新值并列成当前事实。
- 元数据：`case_id`、`access_scope=case_only`、`source_kind=case_evidence`、`is_mock`、`content_hash`、`status=case_current`、`authority=derived_case_state_not_policy` 等。引用以 `本案/{case_id}` 和章节定位；需要核对原件时必须打开案件原始附件/审计记录。
- 存储：沿用项目现有 SQLite 或 PostgreSQL 的知识文档/片段表，不另建向量数据库。当前环境缺 ML 依赖，运行时使用 BM25；将来启用向量/重排前须复核权限过滤和检索评测。
- 增量：Python store 的案件创建、标题、笔记和流程写入后自动同步；Next.js 直接写 PostgreSQL 的财务签署在提交后调用私有重索引接口。案件问答前仍会做一次幂等同步，作为写入故障后的修复。API 启动后台执行全案对账，修复旧案件或漏写快照。
- 失败：直接财务签署已成功但重索引失败时不重放签署；返回 `rag_index_status=retry_on_next_case_query`。普通写入后的索引失败不回滚已提交的业务动作，而记录 `case_knowledge_sync` Bad Case；下次案件问答/启动对账修复并关闭该异常。若数据库完全不可用，异常记录本身也可能失败，仍须依赖服务日志和后续对账。下一阶段可用同事务 outbox 消除跨写入原子性缺口。

## 存量补建与核查

脚本 `scripts/sync-case-knowledge.py` 默认不连库、不写入；PostgreSQL `--apply` 必须提供精确主机和数据库名，SQLite 必须指定已存在的 CRA workbench 文件。它逐案幂等同步并验证文档类型、案件 ID、私有访问范围和非空片段数。

本轮已对当前配置的 PostgreSQL `neondb` 执行一次：**12 个案件、12 个变更、12 个核验通过**；知识片段总数 363。这只证明派生文档在当前库中存在，不证明每个原始附件已解析、生成回答正确或逐案权限满足真实生产要求。

## 已完成模拟案件的历史档案（2026-10-28）

用户看到的“历史案件 0 份”并非案件未保存：当前 PostgreSQL 中已有 12 个案件及各自的 `case_evidence` 私有检索快照。为避免把进行中/阻断案件冒充历史结论，新增 `case_history` 的只读派生档案，仅在**模拟案件、流程状态为 `completed`、启用当前演示知识版本且存在 BP**时生成。文档明确注明“完成流程不等于授信获批”；保留 `case_id`、`bp`、知识版本、状态、内容哈希与来源，按同 BP 过滤检索。案件重新进入处理中时，档案撤回、正文清空、片段删除；案件数据库与本案私有快照继续保留。

`scripts/sync-case-knowledge.py --apply` 现在同时补建/核验历史档案。对当前 Neon 数据库执行后：**12/12 私有快照核验通过，3/3 已完成模拟案件历史档案核验通过**；在线知识接口显示“历史案件 3 份”，均为只读。原有未签核的模拟历史申报资料仍对普通分析师隐藏。此功能没有将 9 个未完成案件转换成历史审批案例，也没有提供真实客户级逐案 ACL 或真实批准结论。

## 验收与后续

已自动测试：新建自动出现文档、改名/笔记/流程刷新、内容哈希幂等、旧值撤回、跨案件检索过滤；后端完整测试和 TypeScript 类型检查通过。仍需联调：浏览器财务签署后 `rag_index_status`、PostgreSQL 写入失败注入、索引更新延迟、真实权限策略，以及已上传 PDF 的原页引用。

真实部署前应补：逐案件 ACL 或明确共享访问政策、附件解析质量门槛、删除/撤回与数据保留规则、事务 outbox/重试告警、P95 同步时延和跨案件泄露评测。没有这些验证，不应把模拟环境的自动入库等同于生产级信用资料管理。
