审查角色：企业 AI 产品负责人、Agent 系统设计审查者

## 1. 总体判断和最关键的问题

### 1.1 总体判断

这是一个**业务边界清楚、技术骨架真实、但文档成熟度领先于运行保障成熟度**的企业 Agent 原型。

作为个人项目，它已经明显强于“聊天框 + Prompt”的演示：项目保留 CRA Excel 交接协议，用固定状态机组织主体核验、财务证据、RAG 起草和人工关卡；代码中存在确定性财务校验、检索前权限过滤、逐句引用/数字校验、独立复核限制和 Bad Case 记录。以上能力有代码和部分自动化测试支持。

但当前还不能把它表述为“企业级闭环已经完成”。最关键的原因不是缺少更多模型或框架，而是**高风险工作流的执行账本、签署绑定、评分闭环、异常恢复和验证证据没有与文档承诺对齐**。更准确的定位是：

> 一个可运行的 CRA 企业信用评审工作台原型，已经验证若干关键控制点；正在补齐可恢复执行、内容哈希签署、确定性评分接线、版本化交付和系统化评测，尚未经过真实业务试点。

### 1.2 最关键的六个问题

1. **文档写成了“已完成”，代码实际是“部分完成”。** `docs/03-agent-and-rag.md` 描述了 input hash 幂等步骤、重启恢复和完整签署，但当前业务表没有 `workflow_steps`、`signoffs`、`artifacts`；`cra/audit.py` 的哈希签署是遗留独立 SQLite 模块，没有接入当前 PostgreSQL 工作台。
2. **额度/评分闭环没有接入主流程。** `external_score` 在阶段枚举中存在，`mock_sap.py` 也有确定性评分实现，但 `run_agent` 没有该分支；风险签署后直接写 Excel，随后进入最终签署。Landing 上“最终额度”人工卡点因此只有 UI/待办形态，没有可核对的评分输入与建议额度产物。
3. **财务校验生成了错误标记，却没有把 error 变成门禁。** 正式 PDF 抽取会生成 `validation_flags`，但随后无条件进入 `financial_signoff`。公司错配预检、公司名复核和 SAP 上年数比对函数存在，却未接入上传路径。
4. **执行可靠性不足以支撑“可恢复、幂等”的宣称。** 一般 Agent 步骤没有 operation/attempt/input hash/result status；仅开放人工任务做了有限去重，财务签署代理做了单点事务保护。固定文件名导出会覆盖上次结果，也没有“结果未知后先对账再重试”的状态。
5. **安全与合规控制有明显缺口。** LLM trace 把完整 messages 和 output 写入本地 JSONL，没有脱敏和保留期；案件聊天 history 的 role 未限制，知识材料 Prompt 也没有显式的“材料中的指令一律视为数据”规则；临时上传文件持续累积。
6. **评测口径过窄且文档数字过时。** 当前后端共收集到 73 个测试，实跑结果是 `72 passed, 1 failed`，不是自测材料中的 54 或 174。22 题离线检索基线确实达到 Hit@5/Recall@20=1.0，但只有 19 个可回答样本、每题一个 gold source；3 个不可回答样本在“不调用模型”的检索模式中直接记为通过，因此不能证明拒答或生成质量。

## 4. 达到“企业应用设计要求”的具体标准

本项目不需要伪装成生产系统。对个人项目，达到企业应用设计深度应满足以下可验证标准：

1. **业务标准**：能说明分析师当前在哪些步骤花时间、哪些错误成本最高、为何 LLM 只适合“读/查/抽/写草稿”，而不是批准授信；至少有专家走查或对照实验方案。
2. **职责标准**：规则负责精确计算和门禁，模型负责非结构化理解与草稿，人工负责主体、证据、风险意见和最终额度；任一职责都能在代码与 UI 中对应。
3. **闭环标准**：一个代表性案件能从 Excel 上传走到版本化导出和独立最终签署；一个错客户/错财报案件能被自动阻断、修正、恢复，并留下审计记录。
4. **执行标准**：每个有副作用的步骤有 operation id、输入版本、状态、结果校验和恢复策略；重复请求不产生重复副作用。
5. **证据标准**：关键数字、政策结论、文件和签署均能定位到 source/version/hash；内容变化后派生结果和签署按依赖失效。
6. **安全标准**：权限在可信服务端执行；材料与用户文本不能修改权限；日志和上下文最小化；文件有生命周期；演示/Mock 始终可见。
7. **评测标准**：检索、生成、工具、权限、异常和端到端分别评估；报告样本、版本、口径、失败项，不用小集 100% 代表生产准确率。
8. **演示标准**：演示脚本只展示真实实现；每个结论都能打开代码、测试或运行结果；未完成能力以 roadmap 展示。

## 5. 按优先级排列的改造方案和实施任务

### 5.1 必须补齐（P0）：最小完整企业闭环

#### P0-A：建立运行事实清单和可追溯版本

- **解决问题**：文档、UI、代码、健康检查和面试话术不一致。
- **取舍**：不先加新模型；先建立 `capability-status.md`，每项只允许五种状态标记。
- **输入/输出**：输入为 commit、配置、health、测试报告；输出为 capability matrix 和 release evidence。
- **涉及模块**：README、PRODUCT、docs/03、docs/05、docs/06、CI。
- **任务**：修正测试数量、混合检索状态、签署/幂等/评分声明；每次 release 自动生成验证摘要。
- **验收**：任何对外陈述都能链接到当前 commit 的代码、测试或运行截图；未验证项不写“通过”。

#### P0-B：补齐 Harness、签署和产物账本

- **解决问题**：无法证明步骤幂等、恢复、签署有效性和文件版本。
- **设计取舍**：保持单 Agent/固定状态机；不引入多 Agent 或分布式队列。使用 PostgreSQL 事务和显式 step runner 即可。
- **核心输入**：case_id、stage、input snapshot ids、actor、tool/prompt/model/rule versions、operation_id。
- **核心输出**：step status（prepared/running/succeeded/failed/unknown）、result refs、validation、attempt、next state。
- **新增/调整数据**：
  - `cra_workflow_run`
  - `cra_workflow_step`
  - `cra_signoff`
  - `cra_artifact`
  - 现有 event 保留为用户可读投影，不承担事实账本职责。
- **接口变化**：`POST /agent/run` 接受/生成 idempotency key；返回 operation status；新增 operation 查询；signoff 接口提交 subject version/hash 和声明。
- **异常处理**：超时后标 unknown，先查数据库/文件 checksum 再决定补偿；不盲目重放。
- **验收**：重复点击、代理超时、服务重启、写文件后数据库提交前中断均有自动化场景；副作用恰好一次或能安全对账。

#### P0-C：打通财务门禁 → 评分 → 版本化 Excel → 最终签署

- **解决问题**：当前流程缺决定最终额度所需的可核对产物。
- **设计取舍**：评分由 `mock_sap.py` 的确定性规则工具执行并标记 Mock；LLM 不算额度、不选审批层级。
- **输入**：已签署 financial snapshot、已签署 qualitative/risk snapshot、FX snapshot、scoring rule version、requested limit。
- **输出**：financial score、qualitative score、overall score、risk class、method、suggested limit、approval level、calculation trace。
- **状态变化**：`risk_signoff → external_score → write_workbook → final_signoff → completed`。
- **门禁**：
  - 财务 error 未关闭：不得签署；
  - warning：签署需接受理由；
  - 任一上游内容变化：评分、Excel、final signoff 失效；
  - final reviewer 不能是 owner，且必须具备当前审批层级权限。
- **验收**：同一输入可复算；数据库、Excel、审计包三处结果一致；修改一个输入后旧结果全部失效但历史保留。

#### P0-D：安全、隐私与输入边界硬化

- 限制 question/history 结构、角色、单条长度、总上下文和轮数。
- Prompt 明确：文档、Excel、用户文本和工具结果均为不可信数据，不能修改系统权限、工具范围和完成条件。
- 只把授权后的必要 chunks 送给模型；对注入、越权索取、无证据、冲突证据分别建测试。
- LLM trace 默认不记正文；增加 correlation_id、版本、token、latency、错误分类和 redaction status。
- preview 临时文件自动清理；正式文件有 source version/checksum/retention；演示环境明确禁止上传真实敏感数据。
- **验收**：敏感字符串扫描为 0；注入测试不会改变权限或工具调用；越权缓存命中为 0。

#### P0-E：建立可发布的评测与演示证据包

- **数据集**：不追求“100 题”形式指标。先覆盖政策、公开资料、历史案例、本案证据、无答案、冲突、注入、权限、错误 PDF、重复执行和恢复；dev 与 holdout 按 source/case 隔离。
- **层级**：
  1. 规则单测：解析、计算、门禁、签署失效。
  2. 契约测试：工具参数/状态/权限/错误码。
  3. RAG 评测：chunk-level Recall@k、MRR/NDCG、引用支持、拒答/误拒答。
  4. E2E：正常案件和关键异常案件。
  5. 用户走查：完成时间、证据查找次数、人工改动、信任问题。
- **发布阻断项**：错误自动放行、越权、陈旧签署有效、重复副作用、数字无出处、导出与数据库不一致均为 0。
- **验收**：生成带 commit/config/model/prompt/rule/data 版本的报告；失败项保留，不通过降低标准“修绿”。

### 5.2 值得增强（P1）：增加面试深度，但不阻断首个闭环

#### P1-A：把“Memory”设计为案件工作记忆

不建设泛化的用户长期偏好记忆。新增由权威数据库重建的 `CaseContext`：目标、对象 ID、已确认字段及来源、当前规范版本、已完成步骤、待办、未决 operation、上下文预算。模型只接收本步需要的切片；用户更正后按 dependency graph 失效相关结果。

面试取舍：RAG 是查外部知识，CaseContext 是保存当前任务事实和进度；历史案件属于受控知识，不是用户记忆。

#### P1-B：封装少量 Skills，而不是把每个函数都叫 Skill

建议首批只做三个 versioned Skill 规范：

1. `cra-financial-evidence`：PDF/页 → 21 字段 + flags + evidence refs；只读/试算，不签署。
2. `cra-risk-draft`：已签事实 + authorized knowledge → 有引用草稿；只生成草稿。
3. `cra-case-qa`：case id + question → grounded answer/refusal；只读。

每个 Skill 必须写触发/不触发、输入 schema、权限、工具、输出、失败状态、版本和 eval。签署、评分落库和文件发布继续由 Harness/服务端控制，不能放给 Skill 自主执行。

#### P1-C：RAG 元数据与实验化启用混合检索

增加 tenant/region/effective_from/effective_to/authority/document_version/parser/index_version。先在同一 holdout 上比较 BM25、vector、hybrid、hybrid+rerank 的质量、延迟、内存和冷启动。只有收益明确才在线启用；否则保留 BM25 是合理产品决策。

#### P1-D：精简脚手架并建立可解释的系统边界

移除或隔离支付、通用 AI 生成器、博客、订阅等与 CRA 无关的 routes/schema/dependencies；README 增加“为何保留/移除 ShipAny 模块”说明。建立 CRA scoped lint 和全仓最终 lint 门禁。

### 5.3 暂不建设（P2/不适用）

| 能力 | 决策 | 面试解释 |
|---|---|---|
| 多 Agent | 暂不建设 | 流程是高风险、强顺序、明确关卡；多 Agent 增加协调和故障面，没有独立权限/知识边界收益 |
| 自由动态规划 | 暂不建设 | 主流程应固定；只允许在检索 query 和错误恢复策略上做受限动态选择 |
| 长期用户偏好 Memory | 不建设 | 授信事实和政策不能被个人偏好污染；需要的是结构化案件状态与审计历史 |
| 微调 | 暂不建设 | 当前瓶颈是流程契约、数据和评测，不是模型风格；先 Prompt/规则/RAG/产品流程 |
| 生产 SAP/D&B/SCASE | 暂不建设 | 个人项目无授权；保持 Mock 并提供 adapter contract 和联调计划更诚实 |
| MCP 写入能力 | 暂不建设 | 现阶段单体直连更简单；MCP 协议不会自动提供业务正确性、权限或幂等 |
| 只读 MCP Demo | P2 可选 | 当需要展示跨宿主复用时，只暴露 `get_case_snapshot`、`search_policy`、`validate_financials`；不暴露 sign/approve/write |

## 6. 典型流程与关键异常流程

### 6.1 典型流程：Northstar 年度复审（目标闭环）

| 步骤 | 输入及来源 | 处理者 | 输出与校验 | 当前状态 |
|---|---|---|---|---|
| 1. Excel 预检 | Northstar CRA Excel | parser + schema rules | checksum、BP、期间、币种、SAP 历史、duplicate branch | 已实现并验证 |
| 2. 建案 | 已通过预检的 source version | Harness | case、source artifact、run、首步 operation | 缺 run/operation ledger |
| 3. 主体核验 | 客户名/国家/地址 + Mock D&B | deterministic matcher | 候选与理由；分析师确认并签主体 snapshot | 候选/人工任务已实现；哈希签署缺失 |
| 4. 财务证据 | 正式 PDF + 已确认主体 + SAP 历史 | extraction Skill + validators | 21 字段、页码、原文、单位、flags；error=0 后签署 | 抽取/flags 已实现；门禁/签署缺失 |
| 5. 风险草稿 | 已签事实 + 授权知识 | risk-draft Skill | 引用草稿、qualitative suggestion、validation report；人工编辑签署 | 基本实现；依赖失效缺失 |
| 6. 模拟评分 | 两个已签 snapshot + Mock rule version | deterministic score tool | 建议额度、风险级别、审批层级、计算轨迹 | 算法存在，未接主流程 |
| 7. 版本化导出 | 已验证 score + 签署内容 | workbook tool | artifact vN、checksum、重开验证 | 现有固定文件覆盖，需改造 |
| 8. 最终复核 | artifact vN + score snapshot | 独立高级分析师 | final signoff 与内容 hash 绑定，案件 completed | 独立人员检查存在；内容绑定缺失 |

完成条件不是“Agent 说完成”，而是：所有必需 step succeeded、三个内容签署和最终复核有效、artifact checksum 可验证、无开放 P0/P1 blocker。

### 6.2 关键异常：上传了错误客户的财报

**当前行为风险**：`check_company` 和 `check_prior_year` 没接入 API；即使 extraction 产生 error flags，系统仍会排入 financial_signoff。

**目标行为**：

1. 上传后先记录 source artifact/version/checksum，状态 `processing`。
2. 文字层存在时，在调用模型前核对公司名、期间、币种；明显错配直接 `needs_correction`。
3. 抽取后再次比较 report company、当前期间、币种、SAP 上年数、会计恒等式和数量级。
4. 任一 blocking error：step=failed_validation，案件保持 `financial_evidence`，创建 correction task 和 L1 Bad Case；不创建 financial signoff。
5. 用户可以解释“母公司合并报表”等 warning，但必须填理由；blocking error 不允许用理由绕过，需有更高权限的 exception policy（若业务确实需要）。
6. 重新上传建立 source v2；v1 和失败记录保留。只重跑受影响步骤。
7. 验证 v2 后再进入签署，后续使用 v2 hash；旧签署、草稿、评分和导出若存在则失效。

验收场景：用现有 `ce_10k_2025.pdf` 与不匹配案件组合；预期系统自动阻断、指出公司/期间/SAP 对比证据，不发生签署或导出，修正后可恢复。

### 8.1 项目定位、目标用户、业务价值和范围

```markdown
## 项目定位

CRA Agent Workbench 是一个面向企业信用分析师的本地演示型工作台。它保留 CRA Excel 作为业务交接协议，把企业主体候选、财报字段抽取、确定性校验、制度检索、风险意见草稿和人工复核组织成一条可审查流程。

## 目标用户与问题

- 信用分析师：减少在 Excel、财报、制度和历史案件之间重复查找、抄录和核对的工作，同时保留对主体、财务证据和风险意见的责任。

## 当前范围

当前未完成或未充分验证的能力包括：工作流 step/operation 账本、内容哈希签署、评分步骤接入、不可变版本化导出、混合检索线上激活、真实系统联调、真实用户效果和生产级隐私/运维控制。

## 非目标

- 不由 LLM 批准授信、修改生产主数据或决定最终额度。
- 不把 Mock SAP/D&B/SCASE 描述成真实接口。
- 不用 RAG 保存精确财务状态或替代确定性计算。
- 不为展示概念而引入多 Agent、长期偏好记忆、微调或有写权限的 MCP。
```

### 8.2 Agent 职责、核心流程及架构说明

```markdown
## Agent 职责

本项目中的 Agent 不是自由行动的聊天机器人，而是受固定状态机和服务端门禁约束的案件协作器。它负责读取非结构化材料、选择受限检索 query、调用确定性工具、生成可编辑草稿和展示证据；它不能授予权限、绕过错误、签署内容或批准额度。

规则与程序负责 Excel 契约、字段类型、财务计算、会计校验、权限、状态转换、幂等、签署有效性和产物校验。模型负责财报抄录、依据材料组织风险草稿和有出处的案件问答。人工负责主体确认、财务证据签署、风险意见签署和独立最终复核。

## 当前流程

Excel 预检 → 建案 → 规则型主体候选 → 人工确认 → 财报抽取/校验 → 人工财务签署 → 授权知识检索 → 风险意见草稿 → 人工风险签署 → Excel 生成 → 独立最终复核。

当前状态机和人工任务已经可运行，但确定性评分尚未接入主路径，签署尚未与内容 hash 绑定，导出仍使用固定文件名覆盖。这些限制在界面和演示中必须明确。

## 目标流程

目标流程在风险签署后增加确定性评分，并以 workflow step、signoff 和 artifact 三类账本保证恢复与审计：

风险签署 → 确定性模拟评分 → 版本化 Excel 与 checksum 校验 → 独立最终签署 → 完成。

每个有副作用的步骤采用 prepare → execute → verify → commit；超时结果进入 unknown 并先对账，不直接重放。任何上游事实、规则或人工修改变化，只使依赖它的草稿、评分、产物和签署失效。
```

### 8.3 企业应用能力、异常处理和验收方案

```markdown
## 企业应用控制

- 身份和权限由 Next.js 会话、数据库 RBAC 和 Python 服务端共同校验，模型输出不能扩大权限。
- 结构化金额和评分由确定性代码计算；RAG 只提供非结构化依据。
- 检索在候选阶段执行 library/case/tenant 范围过滤，禁止先取越权内容再隐藏。
- 文档、Excel、用户问题和工具返回均视为不可信数据，其中的指令不能改变系统规则、权限和完成条件。
- 人工签署绑定对象版本、内容 hash、声明、角色和时间；上游内容变化后自动失效。
- 文件和步骤使用 operation/artifact id；重复请求不产生重复副作用，结果未知时先对账。

## 异常处理

- 缺关键字段或对象有歧义：只追问影响下一步的最少信息。
- 财务 error：保持在证据阶段，创建更正任务和 Bad Case，不进入签署。
- warning：允许有权人填写理由后签署，理由进入审计快照。
- 模型输出格式错误：有限重试；仍失败则使用明确标记的规则型草稿或转人工。
- 引用/数字校验失败：重新检索并重写一次；仍失败则阻断回答并创建人工复核。
- 工具超时或写入结果未知：记录 unknown，查询 operation/artifact 状态后再恢复，不直接重放。
- 依赖不可用：保存已验证进度，向用户说明降级能力；BM25 降级不能被描述成已启用混合检索。

## 验收

发布报告必须包含 commit、环境、模型/Prompt/规则/知识版本、样本和失败项。最低门禁是：类型检查和约定范围 lint/test 全绿；正常 E2E 和错财报 E2E 通过；非法自动推进、陈旧签署、重复副作用、越权泄露、关键数字无出处和导出不一致均为 0。
```

### 8.5 面试项目介绍与有证据的关键决策案例

#### 30 秒项目介绍

> 我做的是一个 CRA 企业信用评审 Agent 工作台。它没有让模型直接做授信，而是保留 Excel 交接和四个人工责任点，让 Agent 负责主体候选、财报抽取、制度检索、引用校验和风险草稿。当前可运行版本已经有固定状态机、确定性财务校验、按案件隔离的 RAG 和 Bad Case 回归；我审查后发现签署 hash、评分接线和幂等恢复仍是缺口，所以我把它定位为可验证原型，而不是生产系统。

#### 90 秒项目介绍

> 我先从业务边界设计，而不是从模型能力出发。信用分析师的重复劳动主要是读 Excel、找主体、抄财报、查制度和写初稿，但主体合并、证据有效性、风险判断和最终额度都有责任风险。因此我选择固定工作流：模型只负责非结构化理解和草稿，精确计算、权限、状态和校验由代码执行，四个关键节点交给人签署。
>
> 在实现上，前端是 Next.js，Python 服务保留 Excel、财报抽取和 RAG 逻辑，PostgreSQL 保存案件、流程、人工任务和知识。RAG 在检索前按知识空间和 case_id 过滤，回答要求逐句引用，数字必须能在引用材料中找到；第二次仍失败就阻断并转人工。当前环境实际是 BM25，向量和重排只做到代码层，还没有在运行环境验证。
>
> 我没有把 demo 成功说成生产成功。当前 73 条 Python 测试有 1 条失败，22 题检索集很小，也没有真实用户效率数据。下一步优先补 workflow operation、内容哈希签署、确定性评分接线和版本化产物，再用正常案件和错客户财报两个 E2E 证明闭环和异常恢复。

#### 关键决策案例 1：为什么不用自由规划 Agent

> CRA 的主路径稳定、依赖明确、错误成本高，所以我没有让模型决定任意下一步，而是用服务端状态机计算唯一允许的动作。模型只在财报抽取、检索 query 和草稿表达这些不确定环节工作。这样牺牲了一部分“自主感”，换来了可审计、可测和不会绕过人工关卡。代码证据是 `run_agent` 按 `current_stage` 分发，而不是使用模型 tool loop。

#### 关键决策案例 2：为什么数字不用 RAG 或 LLM 决定

> 财务数字要能复算、定位和失效。LLM 只抄字段并给页码/原文，代码再做会计恒等式、小计、符号和数量级检查；评分和额度也应由确定性工具计算。RAG 只提供政策和背景，不保存精确业务状态。审查中我还发现 flags 尚未真正阻断签署，这正是我下一步优先修的控制缺口。

#### 关键决策案例 3：混合检索为什么不能直接写成“已上线”

> 项目有 BM25、向量、RRF 和 reranker 的底层代码，但当前 health 显示向量和重排未激活，实际是 BM25 降级。22 题小集上 BM25 已全命中，因此现在不能声称向量带来收益，也不能把缺依赖包装成主动取舍。正确做法是在相同 holdout 上比较质量、延迟和资源，再决定是否上线。

#### 关键决策案例 4：Skills、MCP 和 Memory 怎么取舍

> 当前 Python 模块还不能叫正式 Skills；我计划把财务证据、风险草稿和案件问答封装成带版本、权限和评测的只读 Skill。MCP 只有在跨宿主接企业系统时才有价值，协议本身不解决权限和业务正确性，因此当前不急着加写权限 MCP。Memory 方面，我需要的是结构化案件工作记忆，而不是用户长期偏好；政策和历史案例继续走 RAG，精确状态以数据库为准。
